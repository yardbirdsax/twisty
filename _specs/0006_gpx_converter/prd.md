# Product Requirements Document: GPX Converter

## Overview

The GPX Converter is a CLI feature that transforms Google Maps shared links into GPX files for use in offline-first navigation applications. It bridges the gap between Google Maps' convenient route planning interface and open-source GPS applications like OSMAnd, enabling users to plan routes where they're most productive and execute them where connectivity is unreliable.

## Problem Statement

Users frequently plan routes in Google Maps for outdoor navigation, delivery work, or route exploration. However, when they want to navigate these routes in offline-capable applications like OSMAnd, there is no straightforward way to export the planned route. Currently, users must either:

1. **Manually recreate routes in the target app.** This is time-consuming, error-prone, and defeats the purpose of planning in Google Maps where the interface is optimized for route planning.

2. **Use manual coordinate transcription.** Users manually note waypoints and input them into their GPS app, which is tedious and error-prone for routes with many waypoints.

3. **Abandon the planned route.** Users either accept a suboptimal route generated by their offline app or don't use offline navigation at all.

The lack of a conversion path creates friction and forces users to choose between planning convenience and navigation flexibility.

## Users

**Primary user:** Outdoor enthusiasts, travelers, and navigation app users who plan routes in Google Maps but navigate using offline-capable applications like OSMAnd.

**Context of use:** User plans a driving route in Google Maps, then exports it for use in an offline app (typically before traveling to an area with limited connectivity). The export typically happens immediately after planning.

**Relevant characteristics:** Users value route quality (they plan in Google Maps for a reason) and want to preserve that planning investment when using offline tools.

## Design Principles

### 1. Fidelity Over Simplicity

The exported GPX route must reproduce the Google Maps planned route as accurately as possible. A simplified version (e.g., only start/destination waypoints) would be easier to implement but would violate the user's trust that they're navigating the route they planned. Any deviation from the Google Maps route is a failure mode, so we optimize for accuracy.

### 2. Frictionless Authentication

Users should not need to manage API keys, create Google Cloud projects, or handle credentials manually. Authentication should feel invisible—a one-time browser login that "just works." OAuth with local token storage achieves this; manual API key management does not.

### 3. Fail Loudly

If the conversion cannot complete (invalid link, API error, malformed route), the system should provide a specific, actionable error message. Partial or silent failures are worse than clear rejection because they leave users stranded without understanding what went wrong.

## Feature 1: Convert Google Maps Link to GPX

### Behavioral / Functional Goal

Enable users to export a driving route from a Google Maps shared link into a standards-compliant GPX file that can be imported into offline navigation apps.

### Trigger / Entry Point

User invokes: `twisty gpx --maps-url <shared-link> --out <filename.gpx>`

The system authenticates (if not already authenticated) and processes the link.

### Core Behavior

1. **URL Validation:** Accept the Google Maps shared link and validate that it is a valid Google Maps link.

2. **Authentication:** If the user has not authenticated with Google yet, open a browser to Google's OAuth consent screen. User logs in and grants permission to access the Maps API. The CLI receives an access token and stores it securely for future use.

3. **Route Extraction:** Call the Google Maps API to extract route data from the shared link, including:
   - All waypoints (start location, any intermediate stops, destination)
   - All detailed track points along the route (the polyline/path as rendered by Google Maps)
   - Any turn information or segments

4. **GPX Generation:** Construct a valid GPX 1.1 file containing:
   - A `<trk>` (track) element with all detailed route points as `<trkpt>` entries (for maximum fidelity)
   - A `<wpt>` (waypoint) element for each significant waypoint (start, intermediate stops, destination) with labels

5. **File Output:** Write the GPX file to the specified output path.

6. **Success Feedback:** Print a confirmation message with the file path and basic route stats (e.g., "Route exported: out.gpx (245 waypoints, 1,250 track points)").

### Rules and Constraints

- Only accept valid Google Maps shared links (URLs matching `maps.google.com/maps/dir/...` or similar patterns)
- Only process driving routes; reject links for other route types (walking, transit, etc.)
- If the link is ambiguous or contains multiple route options, use the first/default route
- Waypoint names should be extracted from the Google Maps data (e.g., "Start: Home", "Stop 1: Gas Station", "Destination: Work")
- If a waypoint has no explicit name, use a generic label (e.g., "Waypoint 1")
- Track points should be ordered sequentially along the route
- The output GPX file must be valid according to GPX 1.1 schema
- If any step fails (invalid link, API error, authentication failure), abort immediately with a clear error message and do not write a partial GPX file

### Data Model

**Input:**
```
--maps-url: string (Google Maps shared link URL)
--out: string (output file path for GPX)
```

**Output GPX structure:**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<gpx version="1.1" creator="twisty">
  <metadata>
    <name>Google Maps Route</name>
    <time>2026-04-11T12:34:56Z</time>
  </metadata>
  <wpt lat="40.7128" lon="-74.0060">
    <name>Start: Home</name>
  </wpt>
  <wpt lat="40.7580" lon="-73.9855">
    <name>Destination: Work</name>
  </wpt>
  <trk>
    <name>Driving Route</name>
    <trkseg>
      <trkpt lat="40.7128" lon="-74.0060"/>
      <trkpt lat="40.7135" lon="-74.0059"/>
      <!-- ... many more track points ... -->
      <trkpt lat="40.7580" lon="-73.9855"/>
    </trkseg>
  </trk>
</gpx>
```

## Technical Direction

### Google Maps API Integration

Use the Google Maps Directions API to extract route data from shared links. The API provides:
- Detailed polyline/track points for the route
- Waypoint information (start, destination, intermediate stops)
- Step-by-step turn information if needed

**Rationale:** The Directions API is the canonical source for Google Maps routing data and guarantees fidelity to what the user planned in Google Maps.

### OAuth 2.0 Authentication

Implement PKCE OAuth 2.0 flow following the same pattern used for Gmail authentication in the newsie project. This ensures consistency and follows security best practices.

**Flow:**
1. **Detect missing credentials:** On first invocation (or if token expired and refresh fails), initiate authentication
2. **Start loopback listener:** Open a TCP listener on `127.0.0.1:<random-port>` to receive OAuth callback
3. **Generate PKCE values:** Create a code verifier (random string) and derive its SHA256 challenge
4. **Redirect to Google:** Open user's browser to Google OAuth consent screen with:
   - Scope: `https://www.googleapis.com/auth/maps-platform.routesPreferredApi`
   - PKCE challenge and method (S256)
   - State parameter for CSRF protection
5. **Handle callback:** Loopback listener receives authorization code and state, validates state matches, captures code
6. **Exchange for tokens:** POST to Google token endpoint with code and PKCE verifier (no client secret needed)
7. **Store token pair:** Save access token, refresh token, expiry, and token type to credential store
8. **Refresh on expiry:** When token nears expiry, use refresh token to obtain new access token without user interaction

**Token storage:**
Implement a `CredentialStore` abstraction with the following interface:
```go
type CredentialStore interface {
  Get(key string) (string, error)      // Returns ErrNotFound if absent
  Set(key, value string) error
  Delete(key string) error
}
```

Store the token pair (access token, refresh token, expiry time, token type) as JSON under a namespaced key in the credential store. On macOS, the credential store should use the system keychain for secure storage. On other platforms, use a secure storage mechanism appropriate to the OS.

**Built-in credentials:**
Support built-in OAuth credentials (client ID and secret) that are compiled into the binary. Allow users to override these via the credential store if they wish to use their own Google OAuth application.

**Timeout:** If user doesn't complete authorization within 5 minutes, abort with a clear error message.

**Rationale:** PKCE eliminates the need to store client secrets locally (more secure than manual API key management). The CredentialStore abstraction ensures platform-specific secure storage is handled automatically. This pattern mirrors successful authentication in newsie and other projects, reducing bugs and maintenance burden.

### GPX Generation

Generate GPX output using a Go library (e.g., `github.com/tkrajina/gpxgo/gpx`) or by directly constructing XML with Go's `encoding/xml` package.

**Rationale:** Libraries provide schema validation; hand-building XML is simpler and more transparent if a library isn't available.

### Error Handling

- **Invalid URL:** "Error: not a valid Google Maps shared link. Expected format: maps.google.com/maps/dir/..."
- **Non-driving route:** "Error: only driving routes are supported. This link contains a [route type] route."
- **API authentication error:** "Error: failed to authenticate with Google Maps API. Please try again and re-authenticate."
- **API call failure:** "Error: failed to retrieve route data from Google Maps API. Please verify the link is valid and try again."
- **Write error:** "Error: failed to write GPX file to [path]. Please check permissions and disk space."

### Integration with Existing System

New code lives in:
- `cmd/gpx/` -- Cobra command implementation (flag parsing, orchestration)
- `internal/gpx/` -- Core GPX conversion logic (Google Maps API integration, GPX generation)
- `internal/auth/` -- PKCE OAuth 2.0 implementation (credential store interface, consent flow, token management)

The GPX command integrates with the existing Cobra CLI framework and uses the new `internal/auth/` package for all authentication concerns. The credential store abstraction decouples authentication from storage, allowing platform-specific implementations (keychain on macOS, secure storage on other OSes) without exposing storage details to callers.

## Scope

### Included

- ✓ `twisty gpx --maps-url <url> --out <file>` command
- ✓ Google Maps API integration to extract driving routes
- ✓ OAuth 2.0 authentication flow (browser-based login)
- ✓ GPX generation with waypoints and detailed track
- ✓ Error handling with clear, actionable messages
- ✓ Credential storage and token refresh

### Not Included (Phase 0)

- Walking, cycling, or transit route support
- Batch conversion of multiple links
- Route editing or modification before export
- Import of GPX files into Google Maps (reverse direction)
- Web UI for conversion
- Scheduled or automated exports

## Success Criteria

1. **Functional:** A user can run `twisty gpx --maps-url <url> --out out.gpx` and generate a valid GPX file that imports into OSMAnd without errors.

2. **Fidelity:** The exported GPX route, when navigated in OSMAnd, matches the Google Maps planned route. Measured by visual comparison of OSMAnd's rendered path against Google Maps for 3+ test routes of varying complexity.

3. **Usability:** First-time user can authenticate via OAuth without needing to read documentation or manage API keys.

4. **Reliability:** Conversion succeeds for valid, properly formatted Google Maps shared links and fails with a clear error message for invalid links.

5. **Robustness:** Token refresh happens transparently; users are not prompted to re-authenticate within a 24-hour period under normal usage.

## Non-Goals

- Support for route types other than driving (walking, cycling, transit, etc.)
- Modification of routes after extraction (e.g., adding waypoints, rerouting)
- Visualization of routes in the CLI
- Batch processing of multiple links in a single command
- Integration with cloud storage or automatic backup
- Support for private/non-shared Google Maps links
- Reverse conversion (GPX → Google Maps)
- Support for custom map styling or preferences

## Future Considerations

- **Multiple route types:** Extend to support walking, cycling, and transit routes with type-specific handling
- **Waypoint editing:** Allow users to add, remove, or reorder waypoints before GPX generation
- **Batch export:** Enable conversion of multiple links in one command
- **Reverse import:** Enable importing GPX files back into Google Maps
- **Alternative route options:** If Google Maps offers multiple routes, allow user to select which one to export
- **Elevation data:** Enhance GPX with elevation information if available from Google Maps
- **Integration with map services:** Allow direct import into other map applications beyond OSMAnd
